Model

Every triage is a single request to claude-haiku-4-5. There is no conversation and no tool use - one log in, one structured report out.

  • Local CLI backend (default). Runs claude -p as a subprocess, billed against your own Claude subscription rather than a metered API key.
  • Hosted API backend. Used automatically on Vercel (a serverless function can't hold an interactive claude login session) via the anthropic SDK, billed to a configured ANTHROPIC_API_KEY.
  • Screenshot triage. The same prompt and model, given the image directly (vision) instead of raw log text.

Per distinct failure the model returns: a short failure_type label, what_broke, evidence quoted from the log, a next_step, severity (critical/high/medium/low), a 0-1 confidence, an optional suggested_fix, and a category - the last one is what auto-routes the finding to a team and picks whichever team member currently has the fewest open findings.

RAG pipeline

Optional, local-only (TRIAGE_RAG=1) - never enabled on Vercel or Azure, since its dependencies pull in PyTorch.

  • Knowledge base. 12 known-failure categories (S3 permissions, schema drift, OOM, timeouts, data-quality rejects, expired credentials, throttling, encoding, ...) plus past triage results, de-duplicated, in a local FAISS index.
  • Embeddings. all-MiniLM-L6-v2 via sentence-transformers - free, local, no API key. Vectors are L2-normalized so inner product = cosine similarity.
  • Retrieval. One short query per distinct error-ish log line (max 8), searched separately and merged by best distance - a single whole-log embedding would miss failures past the model's ~256-word-piece window.
  • Prompt. The top 3 matches go in as background context only, explicitly never as evidence the model can cite directly.
  • Fail-soft. A missing package, a model-download failure, or a bad index prints a one-line note and triage proceeds without retrieval.

Known limits, stated plainly:

  • No clean similarity cutoff - right matches and irrelevant filler score in overlapping ranges, so the model is told to judge weak matches itself.
  • Re-triaging a log already in history retrieves its own prior answer as a "similar case."
  • First run downloads a ~90 MB embedding model.

Software

  • Backend: Python, FastAPI, Pydantic (schema validation for the model's structured output), psycopg for Postgres.
  • Frontend: plain HTML/CSS/vanilla JavaScript - no framework, no build step. Four pages: this site's home, triage form, workflow dashboard, and trends.
  • Auth: HMAC-signed, HttpOnly session cookies; passwords stored as salted scrypt hashes.
  • Container: Docker, python:3.12-slim base image (Azure deployment only).

Hardware / hosting

  • Azure App Service (Linux, custom Docker container) - B1 Basic plan, West US 2 - serves the always-on triage form and its JSON API.
  • Vercel - static hosting for this site plus a serverless function for the dashboard's login/findings API. Vercel itself never calls Claude.
  • Neon - serverless Postgres (us-east-1) backing the dashboard, shared by the Azure app, the Vercel API, and a local local_server.py run.
  • Local machine - the Vercel-hosted triage form's other configuration routes requests to local_server.py running on the owner's own Mac, which triages via the claude CLI against their Claude subscription - no API key, nothing billed to a hosted account.
