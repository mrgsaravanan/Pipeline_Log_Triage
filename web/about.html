How to use it

1. Triage a log

  1. Open Triage a log.
  2. Paste the failed run's log, or upload a log file or a screenshot of one (PNG, JPEG, GIF, WebP; images up to 4 MB). Very large logs are cut to a head+tail excerpt.
  3. Click Triage. On a hosted page it calls the Azure server; when running locally it calls python local_server.py on port 8000, which must be started first and needs claude login.
  4. Read the report: one card per distinct failure with what broke, the quoted evidence, the next step, severity and confidence. Export it as Markdown if needed.

2. Work the findings

  1. Sign in at the Workflow dashboard with a username from the list at the bottom of this page.
  2. Each failure is already classified, given a priority, routed to one of three teams and assigned to the member with the fewest open findings.
  3. Filter by status, priority or team (or tick Assigned to me) and click any column to sort. Open a finding to change status, priority, team, assignee, ETA and estimated/actual hours, and to write resolution notes.
  4. Use Export as Markdown or Print / save as PDF to share a finding.
  5. Open Trends and cost for weekly volume, cost and recurring failures.

3. Let failures arrive automatically

Azure Data Factory pipelines and CI jobs can send failures in without anyone pasting a log - see the integrations below. For ADF failures that are waiting in the queue, open the Workflow dashboard and click Run ADF drain; the counter beside it shows how many are queued, and the new findings appear in the table when it finishes.

Integrations

  • Azure Data Factory. Failed pipeline runs are pulled from the factory (python adf.py) or pushed by a Web activity on the pipeline's Failure path to /api/adf/webhook. On Vercel the webhook queues the failure in Postgres and the queue is then triaged with python adf.py --drain on the owner's machine, or with the dashboard's Run ADF drain button: signed-in users see how many ADF failures are queued, and one click starts triage in the background on the Azure server (which holds the Claude login). The page shows progress and refreshes the findings when the queue is empty.
  • Claude through the claude CLI (the owner's subscription) for triage - no billed API key.
  • Postgres (Neon). Every run and finding, its status history and cost live in one database shared by the Azure app, the Vercel dashboard API and the local server.
  • Vercel hosts this site and the dashboard's login/findings API; Azure App Service hosts the always-on triage form and JSON API.
  • CI / GitHub Actions. Any job can post a failed log to /api/triage with an ingest token (example workflow in docs/github-action-example.yml).
  • Slack / Teams and email alerts. Urgent (P0/P1) or recurring findings post to an incoming webhook and email the owning team's on-call address.
  • Log sources. Plain text, JSON-lines, stack traces, IBM DataStage logs, multi-failure logs, non-UTF-8 text and screenshots.
  • Local vector search (optional). The RAG pipeline below adds similar past cases as background context.

Key advantages

  • Root causes, not a wall of text. A failed run is split into its distinct failures, each with evidence quoted straight from the log so it can be checked.
  • Straight to the right people. Auto-classification, priority, team routing and least-loaded assignment remove the manual triage meeting.
  • One place to track it. Status, ETA, hours and resolution notes per finding, with a full status history for audit.
  • Cost and trends visible. Estimated cost per finding from each team's hourly rate, weekly volume, and mean time to resolve.
  • Repeats stand out. Recurring failures are detected by signature and escalated in alerts instead of being fixed once and forgotten.
  • No pay-per-token bill for normal use. Triage runs on the owner's Claude subscription; the dashboard itself never needs a Claude API key.
  • Works with what you have. Paste, upload, screenshot, CI or Azure Data Factory - no agent to install on your pipelines.
  • Safe by default. Signed session cookies, salted password hashes, no passwords on the public page, and only aggregate figures shown without login.

Model

Every triage is a single request to claude-haiku-4-5. There is no conversation and no tool use - one log in, one structured report out.

  • Claude CLI backend (what every deployment uses). Runs claude -p as a subprocess, billed against the owner's Claude subscription rather than a metered API key. It powers the local server and the Azure container, which is given a Claude login token at startup.
  • Vercel never calls Claude. The Vercel site is static pages plus a dashboard API that only reads and writes Postgres. A serverless function can't hold a claude login session, so triage runs on the owner's machine or the Azure container and its results are saved to the shared database.
  • Optional API backend (off by default). The code can call the Anthropic API through the anthropic SDK when TRIAGE_BACKEND=api is set. No deployment turns it on, so no ANTHROPIC_API_KEY is needed or billed.
  • Screenshot triage. The same prompt and model, given the image directly (vision) instead of raw log text.

Per distinct failure the model returns: a short failure_type label, what_broke, evidence quoted from the log, a next_step, severity (critical/high/medium/low), a 0-1 confidence, an optional suggested_fix, and a category - the last one is what auto-routes the finding to a team and picks whichever team member currently has the fewest open findings.

RAG pipeline

Optional, local-only (TRIAGE_RAG=1) - never enabled on Vercel or Azure, since its dependencies pull in PyTorch.

  • Knowledge base. 12 known-failure categories (S3 permissions, schema drift, OOM, timeouts, data-quality rejects, expired credentials, throttling, encoding, ...) plus past triage results, de-duplicated, in a local FAISS index.
  • Embeddings. all-MiniLM-L6-v2 via sentence-transformers - free, local, no API key. Vectors are L2-normalized so inner product = cosine similarity.
  • Retrieval. One short query per distinct error-ish log line (max 8), searched separately and merged by best distance - a single whole-log embedding would miss failures past the model's ~256-word-piece window.
  • Prompt. The top 3 matches go in as background context only, explicitly never as evidence the model can cite directly.
  • Fail-soft. A missing package, a model-download failure, or a bad index prints a one-line note and triage proceeds without retrieval.

Known limits, stated plainly:

  • No clean similarity cutoff - right matches and irrelevant filler score in overlapping ranges, so the model is told to judge weak matches itself.
  • Re-triaging a log already in history retrieves its own prior answer as a "similar case."
  • First run downloads a ~90 MB embedding model.

Software

  • Backend: Python, FastAPI, Pydantic (schema validation for the model's structured output), psycopg for Postgres.
  • Frontend: plain HTML/CSS/vanilla JavaScript - no framework, no build step. Four pages: this site's home, triage form, workflow dashboard, and trends.
  • Auth: HMAC-signed, HttpOnly session cookies; passwords stored as salted scrypt hashes.
  • Container: Docker, python:3.12-slim base image (Azure deployment only).

Hardware / hosting

  • Azure App Service (Linux, custom Docker container) - B1 Basic plan, West US 2 - serves the always-on triage form and its JSON API.
  • Vercel - static hosting for this site plus a serverless function for the dashboard's login/findings API. Vercel itself never calls Claude.
  • Neon - serverless Postgres (us-east-1) backing the dashboard, shared by the Azure app, the Vercel API, and a local local_server.py run.
  • Local machine - the Vercel-hosted triage form's other configuration routes requests to local_server.py running on the owner's own Mac, which triages via the claude CLI against their Claude subscription - no API key, nothing billed to a hosted account.
